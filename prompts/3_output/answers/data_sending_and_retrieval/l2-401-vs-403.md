# L2 What is the difference between a 401 and a 403 status code, and how should a client respond to each?

## Quick Distinction

| Code | Name | Meaning |
|------|------|---------|
| 401  | Unauthorized | **Not authenticated** — the server does not know who you are |
| 403  | Forbidden    | **Not authorized** — the server knows who you are, but you lack permission |

Despite its name, `401 Unauthorized` is really about **authentication**, not authorization.

---

## 401 Unauthorized

The request lacks valid authentication credentials. The server includes a `WWW-Authenticate` header describing what scheme is expected.

**Typical causes:**
- No token / cookie provided.
- Token is expired or malformed.
- API key is missing.

**Client response:**
1. Try to refresh the access token (if using OAuth / JWT refresh tokens).
2. If refresh succeeds, **retry the original request** with the new token.
3. If refresh fails, redirect the user to the login page.

```csharp
var response = await _httpClient.SendAsync(request);

if (response.StatusCode == HttpStatusCode.Unauthorized)
{
    var refreshed = await _tokenService.TryRefreshAsync();

    if (refreshed)
    {
        // Rebuild request (HttpRequestMessage can't be reused)
        var retryRequest = CloneRequest(request);
        retryRequest.Headers.Authorization =
            new AuthenticationHeaderValue("Bearer", _tokenService.AccessToken);

        response = await _httpClient.SendAsync(retryRequest);
    }
    else
    {
        // Refresh failed — user must log in again
        _navigationService.NavigateTo("/login");
        return;
    }
}
```

---

## 403 Forbidden

The server has identified the caller but refuses to fulfill the request because the caller lacks the required permission or role.

**Typical causes:**
- User authenticated as a regular user but accessed an admin endpoint.
- Resource belongs to a different user/tenant.
- Feature flag / subscription tier blocks access.

**Client response:**
- **Do NOT retry** — refreshing a token will not change the permission level.
- Show a "You don't have access" message.
- Log the event for auditing if appropriate.

```csharp
var response = await _httpClient.GetAsync($"/api/admin/reports");

switch (response.StatusCode)
{
    case HttpStatusCode.OK:
        return await response.Content.ReadFromJsonAsync<ReportDto>();

    case HttpStatusCode.Unauthorized:
        // Could work after re-authentication
        await HandleUnauthorizedAsync();
        break;

    case HttpStatusCode.Forbidden:
        // Will NOT work after re-authentication — show permission error
        throw new ForbiddenException("You do not have permission to view reports.");

    default:
        response.EnsureSuccessStatusCode();
        break;
}
```

## Server-Side (ASP.NET Core) Perspective

```csharp
// Middleware returns 401 when no valid JWT is present
services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(...);

// Controller/action returns 403 when policy is not satisfied
[Authorize(Policy = "AdminOnly")]   // authenticated but wrong role → 403
[HttpGet("admin/reports")]
public IActionResult GetReports() => Ok(data);
```

ASP.NET Core's authorization middleware returns:
- `401` when the user is anonymous (no identity established).
- `403` when the user is authenticated but the policy/role requirement fails.

---

## Common Mistake

Some APIs incorrectly return `403` for both unauthenticated and unauthorized requests to avoid leaking whether a resource exists. This is acceptable for security-sensitive resources (e.g., user profiles) but makes token refresh logic harder to implement correctly.

---

## Key Takeaways
- **401**: identity unknown — the client should re-authenticate, then retry.
- **403**: identity known, but permission denied — retrying will not help; show an error.
- Never retry a `403` with a token refresh — it wastes a network round-trip and could exhaust refresh quotas.
