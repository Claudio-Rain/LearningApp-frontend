# L2 When would an API correctly return `400 Bad Request` vs `422 Unprocessable Entity` vs `401 Unauthorized` vs `403 Forbidden`?

## Answer

These four status codes are frequently misused. Each maps to a distinct failure category.

| Code | Category | Root cause |
|---|---|---|
| 400 Bad Request | Malformed request | The server cannot parse or understand the request syntax |
| 422 Unprocessable Entity | Validation failure | The request is syntactically valid but semantically invalid |
| 401 Unauthorized | Authentication missing/invalid | The caller has not proved who they are |
| 403 Forbidden | Authorization denied | The caller is authenticated but lacks permission |

### 400 Bad Request

Return 400 when the request itself is malformed — the server cannot even begin to process it.

Typical causes:
- Invalid JSON / XML syntax in the body
- Required query parameters are missing or have the wrong type
- A header value is unparseable

```csharp
// ASP.NET Core returns 400 automatically when model binding fails
// (e.g., non-numeric value supplied for an int parameter)
[HttpGet("{id:int}")]
public IActionResult GetOrder(int id) { ... }
// GET /orders/abc  →  400 Bad Request (cannot bind "abc" to int)
```

In ASP.NET Core, `[ApiController]` automatically responds with 400 (via `ValidationProblemDetails`) for model binding failures and required-field violations before the action method is even called.

### 422 Unprocessable Entity

Return 422 when the request is syntactically correct (JSON parses fine, types are correct) but the **business rules** are violated.

Typical causes:
- A field value is out of an acceptable range (`quantity: -5`)
- A combination of fields is logically inconsistent (`startDate` is after `endDate`)
- A referenced entity does not exist (`categoryId: 9999` where 9999 is unknown)

```csharp
[HttpPost]
public async Task<IActionResult> CreateOrder(CreateOrderRequest request)
{
    // Request was parsed and model-bound successfully (no 400)
    if (request.Quantity <= 0)
    {
        return UnprocessableEntity(new { error = "Quantity must be greater than zero." });
    }

    if (request.ShipDate < DateTime.UtcNow.Date)
    {
        return UnprocessableEntity(new { error = "ShipDate cannot be in the past." });
    }

    // ...
}
```

> Note: RFC 9110 absorbed 422 from WebDAV. Some teams use 400 for both parsing and validation failures. Using 422 is the more precise choice and is now standard practice in modern REST APIs.

### 401 Unauthorized

Return 401 when the caller has **not authenticated** or the supplied credentials are invalid/expired.

Typical causes:
- No `Authorization` header on a protected endpoint
- Bearer token is expired or has an invalid signature
- API key is missing or unrecognized

```csharp
// ASP.NET Core emits 401 automatically via UseAuthentication()
// when [Authorize] is applied and no valid token is present.

[Authorize]
[HttpGet("profile")]
public IActionResult GetProfile()
{
    // Only reached if authentication succeeded
    return Ok(User.Identity?.Name);
}
```

The `WWW-Authenticate` response header should be included with 401 to tell the client how to authenticate (e.g., `Bearer realm="api"`).

### 403 Forbidden

Return 403 when the caller **is authenticated** (the server knows who they are) but they are not **authorized** to perform the action.

Typical causes:
- A regular user tries to access an admin-only endpoint
- A user tries to modify another user's resource
- A valid API key does not have the required scope

```csharp
[Authorize(Roles = "Admin")]
[HttpDelete("{id}")]
public async Task<IActionResult> DeleteUser(int id)
{
    // ASP.NET Core returns 403 automatically if the authenticated user
    // is not in the "Admin" role.
    await _userService.DeleteAsync(id);
    return NoContent();
}
```

### Side-by-side Comparison

```
Request arrives with no token  →  401  (who are you?)
Request arrives with valid token but wrong role  →  403  (I know who you are, but no)
Request arrives with valid token, correct role, but body is unparseable JSON  →  400
Request arrives with valid token, correct role, parseable JSON, but negative price  →  422
```

### Key Takeaways

- **400** — I cannot parse or understand the request.
- **422** — I understood the request but it violates business rules.
- **401** — Prove who you are first.
- **403** — I know who you are, and you are not allowed.
- Never return 403 when you mean 401 — doing so leaks that the resource exists to unauthenticated callers and prevents clients from re-trying with credentials.
